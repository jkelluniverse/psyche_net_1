## 1. The lens lane (`/src/engine/lens/`)

**What it is:** birth data → astrology-api.io → `ChartImport` row (raw JSON preserved) → a **deterministic, versioned mapping** produces lens `PsycheNode`s: **domain-typed** (D-R4: a lens hypothesis about a protection is `type=PROTECTION, provenance=LENS` — never `type=LENS`, which is deprecated-never-written and rejected by DB CHECK), `state=HYPOTHESIS`, `mass=0`, `confidence=` the hypothesis floor (0.15, config), `chartImportId` FK set, `lensMapVersion` stamped. All writes go through the graph writer — the lane is the third of the writer's three sanctioned upstream computers (schema banner), and it does **not** pass through the gate, deliberately: the gate verifies quotes against source text, and lens nodes have neither, so a gate pass would be trivially true — a check that cannot fail launders trust instead of creating it.

**The mapping is code, not model.** A versioned table (`lens-map.v1.ts`) from chart features (e.g., HD type/authority/defined centers; natal placements) to hypothesis node templates — each with a **domain `type`**, a plain-language label ("may protect independence under pressure"), an `ontologyKey`, and a `priority` (integer, for the ghost budget). Same chart → same ghosts, always. The lens map pins **key→type one-to-one** (a map-version bump that changes a key's type fails CI — an update-in-place must never cross-type mutate). No LLM anywhere in this lane; an LLM summarizer for chart *prose* is post-pilot and would never create nodes regardless (LAW 4 applies to lanes too: only the mapping creates, and only lived words ever charge).

**The ontology direction rule (D-R1), enforced structurally (r2 A-8):** the shared ontology is **chart-agnostic, and the lens map projects into it.** Lens-map targets must be existing psychological keys (e.g. `protection.independence`); **no chart-specific key ever enters the ontology the proposer sees.** Enforcement, not policy prose: (a) lens-map targets are a **typed subset** — `ontologyKey: OntologyKey`, a union generated from the ontology module (single source of truth), so an unknown key is a compile error; (b) **CI job (named, executable):** a change-set that modifies both the ontology config and `lens-map.*` fails the co-modification check in CI — not review convention, a script; (c) the **naming rule** as a CI lint — keys describe psychology, never chart features; the denylist of system terms (centers, gates, houses, signs, authorities) runs over lens-map keys on every commit; (d) **runtime fail-closed:** an import whose mapping references an unknown key is refused and logged, never guessed through. Under this rule the proposer sees the same global vocabulary for every user, chart or no chart — a global vocabulary is not a hypothesis, so nothing user-specific can leak. The residual population-level gradient (the ontology slowly growing chart-shaped) is *measured*: the eval corpus carries a lens-confirmation case (§5 test 9, eval-scored) whose match rate is tracked per ontology version.

**Rules:**
- v1 systems: Human Design + Western natal (or HD only if the API integration fights back — cut-line applies). `system` recorded per import.
- **Ghost budget:** cap materialized ghosts (config key `lens.ghostBudget`, ~9–15) ranked by a **total order: priority-strength first (1 = strongest), then ontologyKey asc, then label asc** (applied before the cap). **Diversity floor (Jacob, post-FINAL):** at least `lens.minTier3Ghosts` (config, default 2) tier-3 ghosts survive the cut when the chart offers them — the lowest-ranked non-tier-3 selections are evicted for them, deterministically. **Charged ghosts live OUTSIDE the budget** — they've earned their place; the cap governs uncharged hypotheses only (so a well-confirmed chart never starves new hypotheses, and archiving never touches a ghost the person's words have spoken to).
- **Idempotency is structural, not aspirational:** imports are keyed by a canonical `chartFingerprint` (hash of normalized birth inputs + resolved timezone + provider id — never the provider's JSON bytes), with `@@unique([userId, system, chartFingerprint])`; lens nodes upsert under a **partial unique index** (`(userId, ontologyKey) WHERE provenance='LENS' AND archivedAt IS NULL`; `ontologyKey` NOT NULL for LENS). The import runs in a **transaction** (fingerprint → ChartImport upsert → node upserts) with retry on serialization failure — concurrent imports cannot double-mint. A `lensMapVersion` bump re-runs the mapping: unchanged keys update in place, removed keys archive their **uncharged** ghosts, and CHARGED ghosts are never auto-archived — they sever gracefully per §7's cascade rule. This mirrors the gate spec's shadow-rekey duty.
- Birth data is quasi-special-category PII: transported to the chart API over TLS, raw response stored, provider + retention logged in the §7.1 governance bundle.
- Birth-data **intake** is app-layer work; the seam contract: intake delivers `{birthDate, birthTime, birthPlace, tzResolved}` validated; the lane owns everything after.
- **No lens node is ever created from extracted text**, and no extracted node ever gets `provenance=LENS`. The lanes never cross except in §3 — and, since gate v1.7, not even the gate's dedupe can cross them (test 19 pins it).

**Failure modes:** API down/malformed → import recorded with `ChartImport.status=error`, zero nodes, retryable — never a partial ghost sky. Unknown chart feature → skipped and logged, never guessed into a node. Unknown ontology key → the whole import refused (fail-closed, above).

## 2. The renderer (`/src/app/(sky)/` + `/src/engine/sky-projection/`)

**Data flow:** persisted graph → `skyProjection(nodes, edges, now, seed, viewer, config)` (pure function → a `SkyViewModel`) → cosmos.gl v3. The projection is the ONLY place domain values become visual values, and it is unit-testable without a GPU. `seed` is explicit (= stable hash of userId); **`viewer` is the viewer context** (role + consentScope-derived visibility — the WOUND veil's carrier, r2 A-4); `config` is the versioned renderer config; the emitted view model carries `projectionVersion`. **Honest determinism boundary:** the VIEW MODEL is deterministic (same inputs → same view model, test 4); GPU force-layout positions are NOT reproducible across devices/drivers even with a fixed seed — demos must never claim "the same sky every time," only the same *content*.

**Structural input honesty:** the projection's input types are persisted views only (`PersistedNodeView`, `PersistedEdgeView`); `ShadowCandidate[]` is type-level unrepresentable as projection input (test 12 carries the `@ts-expect-error` fixture). Shadow-lane material is held, not shown — enforced by the type system, not convention.

**Effective evidence (r2 A-2):** `PersistedNodeView` carries `effectiveEvidence` = the node's own Evidence rows ∪ evidence linked via `HypothesisEvidenceLink` (each entry with authorship, spanStart/spanEnd, occurredAt, polarity, conferring, normalizationVersion). Everything evidence-driven in the grammar — brightness, uncertainty, the tap panel — consumes `effectiveEvidence`, so a charged ghost brightens and explains itself exactly like an extracted node. The union is canonically sorted (occurredAt, then evidenceId) for byte-determinism; double-counting is structurally impossible in v1 and kept so on purpose (LENS nodes have no own evidence; the matcher links only extracted nodes' rows); and **both recompute and `effectiveEvidence` consume only links with `invalidatedAt IS NULL` and sources with `invalidatedAt IS NULL`** — the one-word WHERE clause, written down. A row whose source event was LAW-8-erased is fail-closed: not rendered, never sliced; a ghost with zero surviving effective evidence reverts to the provenance copy. The `SkyViewModel` additionally carries `LensMatchLinkView[]` (`{lensNodeId, extractedNodeId, evidenceIds}`) — a **non-persisted rendering overlay** computed from the link table, which is what the matched-pair treatment renders from.

**The rendering grammar (each mapping versioned in `rendererConfig`, whose defaults are checked into the repo with a canonical-view snapshot per version):**
- `mass` → node size (log scale; mass 0 = minimum ghost radius).
- **Brightness** → a **named, versioned recency function** `brightness(effectiveEvidence.occurredAt[], now)` (half-life in config) computed inside the projection. The name is `brightness` everywhere in code — never "luminosity"; the persisted `luminosity` column is **not consumed** (its formula is still deferred per the schema's own guard), and a test asserts the projection never reads it. DORMANT nodes dim, never vanish.
- `confidence` → **always visible** (LAW 5): opacity floor + a subtle uncertainty ring (band constants in rendererConfig). **Edges too:** edge `confidence` maps to opacity/dash treatment (versioned config).
- `state` → styling: HYPOTHESIS = **ghost styling** (dashed ring, reduced saturation, explicit "hypothesis" badge on tap); CONTRADICTED = visibly dimmed/struck, still present; IGNITED = the ceremony style; QUESTIONED/LOOSENING per the change arc.
- **WOUND gating (D-R5 + r2 A-4 — a property of the projection, never a per-surface courtesy):** veiling is computed **into the view model** by `skyProjection` from the `viewer` parameter — a veiled node's view-model entry carries the veil copy, never the raw label — so EVERY renderer of the model (canvas, list view, realization toast, anything future) inherits the veil for free. WOUND nodes render **veiled-but-present** in INDIVIDUAL skins (LAW 5: never falsely complete; LAW 7: never raw at 1 a.m.); full visibility for the PRACTITIONER viewer in supervised skins per consentScope — and **v1 has no release carrier, so a client viewing their own map within a supervised engagement is veiled ALWAYS (fail-closed)**: the per-node release state (practitioner-authored, feeding the projection through `viewer.releasedNodeIds`) is §7.1 bundle work with its seam reserved, and the spec says so instead of implying a mechanism that doesn't exist (D9's mediation flow; the permissive misreading is closed). The veil's register: copy calm and forward-looking ("something to explore together next session"), never ominous; veiled nodes render **singly, never as a clustered mass**; the crisis classifier's operation is fully independent of the veil (operationalized: classifier output invariant under veil-flag flip on identical input, plus an import-boundary lint — the classifier module cannot import rendererConfig). Gating config in `rendererConfig.woundGate`; the pilot-feedback fallback (practitioner-release-only visibility) remains a config change, not an architecture change (§7.1).
- Edges → line weight by strength, style by type; shadow-lane edges are **not rendered at all** (structurally excluded, above).
- **Matched pairs render LINKED, never merged and never as two unrelated stars:** rendered from `LensMatchLinkView` (badge/caption constants in rendererConfig) so one construct never reads as two bodies.
- The **edge of the unexplored** (LAW 5): a soft unexplored fringe — an honest static affordance (config-owned copy + treatment; v1 does not pretend to compute "how much is unexplored"). Never blank, never falsely complete. (Whether the static affordance still reads honestly on mature maps is a named §7.1 pilot watch.)

**Hard invariants (from CLAUDE.md — restated because this module is where they bite):**
- **Domain/rendering separation:** force-layout positions are stochastic artifacts. No coordinate is persisted into domain state, read as meaning, or fed back into anything. Migration 6 dropped `PsycheNode.x/y/colorHint`; test 5 asserts at the schema level that no coordinate columns exist on domain tables. Layout uses the fixed per-user seed for session-to-session visual continuity — a *rendering* convenience, not a semantic claim; any future layout cache lives in a rendering-only store keyed by node id, never on domain tables. Nothing in copy or UI may imply proximity = psychological relatedness beyond the edges actually drawn.
- **cosmos.gl v3 only** (`@cosmos.gl/graph`, MIT; never `@cosmograph/cosmograph`): async init — constructor returns immediately, public methods queue until `graph.ready`; use the v3 API, no pre-v3 tutorial code. Exact version pinned in the lockfile; SPDX recorded at install. The integration test is a **smoke test** (spies on calls; assumes nothing about internal queue structure — that contract can shift across minor versions).
- **Reduced-motion / non-spatial fallback:** `prefers-reduced-motion` → static layout, no animated transitions; plus the full **list view** — nodes AND edges grouped by type/state, keyboard navigable, evidence accessible — **shipped inside the ghost-sky milestone** (LAW 5: no information may exist only spatially or in motion). The list view is the **canonical accessible surface** and is content-parity property-tested against the same (veiled) view model — which is how the veil provably holds there (test 10).
- **Mobile touch is first-class** (the demo is on their phone): tap = select, pinch = zoom. Evidence has an **explicit affordance in the node panel**; long-press remains a secondary path, never the only one. Test on a real phone, not devtools emulation.

**Tap-for-evidence:** node → panel with label, type, state, plain-language confidence, and its `effectiveEvidence` list — each row rendered by slicing `SourceEvent.content` with `spanStart/spanEnd` (the spans the NFKC index map exists to protect) — **sliced server-side** (a canonical-snippet endpoint returns the slice by persisted spans; a slice/`quote` mismatch renders as a visible error, never a silent fallback), with `occurredAt` shown (temporal honesty), `authorship` present and rendered (practitioner-authored evidence visibly marked non-conferring), and **COUNTERVAILING evidence visually distinct** with the gate §1.1 model-assigned-polarity note. Hypothesis nodes with zero effective evidence show their provenance instead: "From your Human Design chart — nothing in your words yet confirms this." On a charged or contradicted ghost, the panel shows **which independently-extracted words did it** ("your chart guessed this; on June 3rd you said this") — rendered from `effectiveEvidence` + the match-link overlay. In SUPERVISED mode, when a second COUNTERVAILING sighting exists but the confirmation carrier isn't deployed (§7 migration 8), the panel shows an explicit **"pending confirmation"** state — fail-closed, never silent.

**Realization events (v1 minimal):** when a pass materializes/charges nodes, the new/changed nodes animate in via cosmos v3 transitions and a small toast names them — **from the veiled view model**, so a veiled node's realization renders with the calm veil copy, never the raw label (the celebration surface cannot bypass the veil; test 10 asserts it). The full ceremony choreography is post-pilot. (LAW 6: the animation celebrates *validated evidence events* only — never streaks, never variable-ratio surprise.)

## 3. The hypothesis matcher (`/src/engine/hypothesis-match/`)

The blinding invariant's completion: the **deterministic, post-gate** module that may see both worlds. The matcher compares validated EXTRACTED nodes/evidence against standing **LENS** hypotheses and updates hypothesis state. **LENS-only in v1 (D-R3):** BECOMING matching is owned by the gate's in-gate label-matcher (gate spec §7). Precedence, pinned: **gate own-provenance dedupe → gate becoming-label merge → post-gate lens matcher.** Since gate v1.7, the gate's dedupe cannot touch a LENS node (test 19), so this module is provably the only charging path for lens hypotheses.

- **Match rule (deterministic, versioned `matchRuleVersion`):** v1 = same **domain `type`** + same `ontologyKey` (exact key match only; no embeddings, no LLM similarity — logged as post-pilot). On match: supporting evidence accumulates charge toward `HYPOTHESIS → ACTIVE`; COUNTERVAILING evidence (under the §1.1 guards — recurrence ≥2 distinct events in SOLO mode, or practitioner confirmation in SUPERVISED) → `CONTRADICTED`.
- **Honest v1 reach:** CONTRADICTED is structurally rare in v1 — a blinded proposer assigns polarity relative to the *extracted* node and cannot tag opposition to a hypothesis it cannot see; the realistic v1 path to CONTRADICTED is affirm-then-deny of the same key. The §2 copy reflects this; the real (semantic) matcher remains the §7.1 bundle item.

### 3.1 The charge carrier (how a match becomes state — and un-becomes it)

- **Evidence is LINKED, never copied (D-R2):** one span, one `Evidence` row, referenced twice. The matcher writes a link record (`HypothesisEvidenceLink`: evidenceId → hypothesis nodeId, matchRuleVersion, matchedAt, runId FK) through the **graph writer** — the extracted node's rows stay intact and single-owner; no duplicate rows enter mass math.
- **Arithmetic is the gate's, imported:** the hypothesis's mass, confidence, and state are recomputed by calling the **gate's exported pure functions** — the concrete import path is `/src/engine/citation-gate/mass`, `/confidence`, `/state` (mass §6.2, confidence §6.3, `nextState` §6.4) — over the merged evidence set (own ∪ linked). Reuse is mandated; reimplementation is banned. A matcher unit test asserts the algorithm versions it stamps equal the gate's for the same recompute (version-skew tripwire).
- **Practitioner confirmation is an OVERLAY, never an arithmetic input (D-R7):** confirmation is **authority, not evidence** — putting it into the gate's `nextState` would launder an authority action into the evidence-arithmetic path (the function that answers "what do the person's words justify?" must never answer "…adjusted by who vouched"). The overlay is applied by the matcher AFTER `nextState`, documented as a distinct input class, not a reimplementation. Three constraints, structural: (1) **its own carrier** — `HypothesisConfirmation` records who confirmed, when, and which MatcherRun applied it (practitioner-action provenance, arriving early from the governance bundle); (2) **reversible and contestable** by the user per the bundle's contestability entry — withdrawal recomputes via trigger 4, and severance of the practitioner relationship withdraws the overlay's effect (the underlying evidence-derived state stands); (3) **state only, never mass** — a confirmation can move HYPOTHESIS→ACTIVE (or ground a CONTRADICTED) as an authority act, but mass remains a pure function of conferring evidence forever: a confirmed-but-evidence-thin node LOOKS confirmed-but-thin on the sky (LAW 5 applied to the practitioner too).
- **The live-join rule:** the matcher builds the gate functions' `EvidenceRecord[]` input for linked rows by **live-join at compute time** — authorship and `sourceInvalidatedAt` read from the current SourceEvent, never cached from link time — so linked evidence obeys **exactly** the gate's invalidation-aware mass semantics: same filter, same definition, imported, never restated.
- **The retraction API (D-R6 — the choke-point that makes the triggers true):** the graph writer owns a **retraction API** — the single sanctioned mutation surface for `SourceEvent.invalidatedAt`/`supersededById`, Evidence erasure, and the future LAW-8 path (schema banner: "a retraction performed anywhere else is a bug"). It is a **choke-point, not a retention mechanism**: LAW-8 erasure flowing through it truly erases — tombstones carry audit metadata only (`evidenceIdWas`, causes, stamps), never content. The retraction surface belongs to the **matcher build stage** (§6, migration 8 scope). The recompute duty covers **every affected derived value, not hypotheses alone**: a retraction also recomputes the stored mass/confidence/state of the EXTRACTED nodes whose evidence it touched (same gate functions, same transaction) — the gate's invalidation-aware filter finally has its named trigger for stored values. Node ARCHIVAL is not a retraction class: archiving an extracted node does not un-charge the ghosts its evidence charged — its evidence rows remain valid, and mass counts evidence, not nodes.
- **Recompute triggers (the WHEN):**
  1. **On match** — a pass's newly validated extracted material matches a standing hypothesis (the original trigger).
  2. **On retraction** — any invalidation, supersession, or LAW-8 erasure touching a `SourceEvent` or `Evidence` row referenced by a `HypothesisEvidenceLink` recomputes the affected hypotheses **synchronously, inside the retraction transaction** (per-person graphs are dozens-to-low-hundreds of nodes; there is nothing to queue, and a crash can never land between retraction and recompute — the divergence window does not exist). If async ever becomes necessary, a transactional outbox row gets named in §7 FIRST. Un-confirming must un-tell: the person who retracts the words that confirmed their chart must see the sky stop saying the chart was right.
  3. **On import/remap** — a lens import or `lensMapVersion` remap runs a **full-graph matcher run** for that user (new/changed ghosts vs. ALL standing extracted nodes), inside the import transaction, serialized per user; `MatcherRun.trigger` carries the IMPORT_REMAP cause with chartImportId/lensMapVersion. Delta-only matching would silently fail the chart-added-after-journaling flow — which is the demo script itself.
  4. **On confirmation** — a `HypothesisConfirmation` write or withdrawal recomputes the named hypothesis, transactionally, same pattern (D-R7 overlay, above).
- **Link lifecycle (with its DB mechanics — r3 A-3):** link rows are **invalidated, never silently cascaded**, when their Evidence row is erased: the retraction transaction sets `invalidatedAt` + `invalidationCause` (SOURCE_INVALIDATED | LAW8_ERASURE | MANUAL) + the invalidating run id, **verifies the insert-time `evidenceIdWas` copy** (the copy is made when the link is CREATED — §7; copy-at-insert is safe under every cascade ordering, where copy-at-retraction would read NULL after a SetNull — the audit survives the FK as id only, never content), THEN deletes the Evidence row (`evidenceId` is nullable, `onDelete: SetNull`; uniqueness is a partial unique over non-null evidenceIds), then recomputes — one transaction, in that order. **SourceEvent erasure cascades to its Evidence rows first** (the `quote` column is a verbatim copy of the person's words — erasure that leaves the words in a different table isn't erasure), then link invalidation fires. A hypothesis whose last conferring link dies recomputes to mass 0 and reverts state per `nextState`. The arithmetic of absence is stated, not implied: **absence needs no positive carrier — the merged set is simply smaller, and mass is a pure function of the surviving records.**
- **Mode guard is structural:** the matcher consumes a versioned `MatcherConfig` carrying `mode: SOLO | SUPERVISED` (mirroring `GateConfig`) — a single model-labeled COUNTERVAILING quote never auto-contradicts in SOLO, by the same shape of code that enforces it in the gate.
- **Every write is stamped and replayable:** each transition persists `matchRuleVersion` + the three algorithm versions + `computedAt`; every run persists a **`MatcherRun`** row whose `inputs JSON` holds the trigger + prior hypothesis states, with links derived from the `runId` FK on the link table — the derivation object that makes "why is this ghost ACTIVE" answerable and test 7's replay assertable against production history.
- The matcher **never creates nodes and never runs during extraction.** The proposer's next pass never sees hypotheses (its `priorExtractedNodes` filter is untouched — test 7 ASSERTS byte-identity of the proposer's serialized context before/after a matcher run; the byte-identity form is deliberate and stays: the serializer is deterministic and allowlist-based, and a "semantic predicate" would reintroduce exactly the judgment layer where leaks hide — r2 rejection R-1).
