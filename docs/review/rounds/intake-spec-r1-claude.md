# REVIEW-01 — Intake Spec, Round 1 (Claude lane)

**Spec reviewed:** Seven Sparks Intake — Module Specification, **v1.0** (`/docs/intake-spec.md`)
**Reviewed against:** CLAUDE.md; master concept v1.1 (§5.1, §7); proposer spec v1.4-FINAL; renderer-lens spec v1.3-FINAL; `src/engine/extraction/run-pass.ts`; `src/engine/crisis/classifier.ts`; `prisma/schema.prisma`; `src/engine/graph-writer/writer.ts` (verification only, per scope notes)
**Scope rulings honored:** the per-answer immediate reflect is treated as the sanctioned, ruled exception (its *argument* is stress-tested under MAJOR-2, its existence is not flagged); prompt-copy wording is not reviewed; copy-*system* findings are.

**Verdict: Request Revisions** — the spine (reuse the real pass entry point per answer) is genuinely sound and better-supported by the code than the spec even claims, but the closing ceremony depends on a write path that does not exist and is currently banned by the schema's own banner, and the per-answer mechanism has no concurrency/ordering contract against an entry point whose watermark semantics actively punish that omission.

---

## CRITICAL

### C-1. The becoming seed ceremony (§4) depends on a lane that does not exist, that the schema banner forbids as written, and whose evidence carrier is unspecified — while the spec claims "no new trust machinery"

**Observation.** §4: *"Accept → a BECOMING node via its own lane (DECLARATION evidence, mass 0, seed-styled)."* Verified against the codebase:

- **No becoming lane exists.** No module under `/src/engine/` creates BECOMING nodes. Grep for BECOMING-creating code finds only the gate's *ignition* arithmetic (`citation-gate/state.ts` — consumes an already-existing seed), the contract types, and negative tests asserting BECOMING is *unextractable*. The lane §4 routes through is unbuilt and unspecified in any document.
- **The schema banner contradicts the route.** `schema.prisma` (lines 182–202): the writer has *"exactly THREE sanctioned upstream computers"* — gate, hypothesis matcher, lens lane — and *"Anything else writing these tables is a bug, not a fourth author."* A becoming lane is a fourth author. Legal, but only via an explicit banner amendment + a named write surface on the writer, which no spec (this one, proposer, renderer-lens) owns.
- **"DECLARATION evidence" has no carrier.** An `Evidence` row requires a real `sourceEventId` + verbatim spans (writer header: `validated = true` DB CHECK). The seed statement is the person's *edited* words — after editing, it is not verbatim in the spark-7 `SourceEvent`, so it cannot cite it. Does the accepted seed statement become its own `SourceEvent`? Under which `SourceKind`? (The enum has none for a becoming declaration; `WORKSHEET_ANSWER` is unclaimed prose.) Does that evidence pass the gate? It can't — the gate processes `ProposerOutput`, and BECOMING is structurally unrepresentable there (`ExtractableNodeType`, contract v2.1). So the DECLARATION evidence needs its own deterministic validation path — which is precisely **new trust machinery**, directly contradicting the spec's headline claim ("the module adds sequencing, prompts, voice, and pacing — no new trust machinery") and test 1's "zero intake-specific extraction code paths."
- **The drafting mechanism is unnamed.** "A one-line editable seed statement drafted FROM their answer" — drafted by *what*? If by an LLM, that is a new model-touched user-facing surface with none of the proposer spec's containment; if deterministic (e.g., a template over the spark-7 answer), say so. It cannot be "reuse the extraction," because extraction cannot produce BECOMING candidates by design.

**Why it matters.** This is the intake's closing ceremony and one of master concept §7's IN items (#4). It is the only part of the flow that writes graph state outside the proven pipeline, it sits directly on LAW 3 (authored intentions, mass 0) — and right now the spec waves at "its own lane" as if it exists. A builder reaching §4 in week N discovers an undesigned write surface, a schema-banner amendment, a possible new SourceKind, and an unanswered gate-bypass question, all inside the demo's money-shot week. Test 5 (becoming consent) cannot even be written against this.

**Recommended action.** Either (a) this spec owns the seam contract: name the becoming lane as the writer's **fourth sanctioned upstream computer** (banner amendment named as a schema delta), define the declaration carrier (recommended: accepted seed statement → its own `SourceEvent`, new `SourceKind` `BECOMING_DECLARATION` or documented reuse of `WORKSHEET_ANSWER`; Evidence row cites the full span of that event verbatim — deterministic, gate-exempt for the same *stated* reason as the lens lane: a check that cannot fail launders trust), pin the drafting mechanism (deterministic template, or model-drafted with an explicit "this is a draft — it becomes real only as your edit" honesty rule), and drop or scope the "no new trust machinery" claim honestly; or (b) declare the becoming lane a blocking upstream dependency with its own mini-spec before this module's §9 build order reaches the ceremony. (a) is better — this spec is the lane's only v1 consumer.

### C-2. The consequence loop has no concurrency/ordering contract, and `run-pass.ts`'s real watermark semantics make the unspecified case corrupting, not just ugly

**Observation.** Verified line-by-line against `runExtractionPass`:

1. **Nothing serializes passes per user.** `loadUnextractedSources` selects sources with `ingestedAt > lastCompleteRun.startedAt`. If answer N's pass is still running when answer N+1 submits and fires its pass (fast typist, instant skip-then-answer, impatient demo subject), pass N+1's watermark is still pass N−1's — it loads **both** answer N and answer N+1 while pass N is concurrently processing answer N. Answer N is extracted twice. Double-extraction inflates `ShadowCandidate.timesSeen`, so **a single mention can cross the recurrence threshold and materialize a node from one utterance** — an evidence-mandate corruption (LAW 1's recurrence discipline defeated by a race), not merely duplicate work.
2. **The lost-answer window.** Sources are loaded *before* the run row is created; the next pass's watermark is this run's `startedAt` (row-creation time). Any event ingested in the window between load and create has `ingestedAt < startedAt` and is **never eligible for any future pass** — silently unmapped words, exactly the "evidence mandate violated by omission" failure §10.5 of the proposer spec exists to prevent. Millisecond-scale under batched journaling; intake's per-answer cadence is the one caller that makes it live.
3. **Failed-pass mis-attribution.** On error the run records `status="error"` and **rethrows**; failed runs don't advance the watermark, so answer N's material silently rides along in answer N+1's pass — and the between-screens beat, whose whole contract is "each answer renders **its** consequence," attributes answer N's stars to answer N+1. The `ReflectSummary` is per-run, not per-source; nothing in the spec knows this can happen.

The only fix consistent with the spec's pedagogy is strict serialization — answer N's pass completes (or is definitively abandoned) before answer N+1 can submit — and the spec never states it. §2 states the happy path only.

**Why it matters.** This is the spec's central mechanism. The three behaviors above are not hypothetical: they are what the real entry point does today when called the way §2 calls it. Two of them corrupt graph state (double-count recurrence; permanently lost words); the third breaks the one sentence the master concept calls the governing rule of intake. Test 1 asserts intake flows "identically to a journal entry" — true and insufficient, because the journal's batched/async cadence never exercises these races and intake's cadence is built out of them.

**Recommended action.** Add a "Concurrency & ordering" subsection to §2 with, at minimum: (a) **one in-flight pass per user, enforced** (spec whether by UI gating — submit disabled until the beat resolves — or a per-user run lock in the orchestration; name which); (b) a required fix or explicit workaround for the load-before-create watermark window (e.g., create the run row *first* and load sources against its own `startedAt`, or an intake-side check via `countUnextractedSources` before enabling the next submit); (c) the mis-attribution rule for the retry path: if a pass covers >1 answer, the beat's copy must say so honestly ("catching up on your last two answers…") — never attribute a merged delta to a single answer. Add a test: rapid submit of two answers produces exactly two runs, no source extracted twice, no source stranded (this is the intake-shaped twin of test 1, and it's the one that would actually have caught all three).

## MAJOR

### M-1. The "existing" crisis floor does not exist as wiring — intake is the first surface that must build it, and the spec disclaims exactly that work

**Observation.** §2: *"The crisis floor runs on every answer unconditionally (existing invariant; intake changes nothing about it)."* Verified: `classifyCrisis` (`src/engine/crisis/classifier.ts`) exists and is well-tested — and has **zero production callers**. There is no `/src/app/` directory in the repo, no ingest module, nothing that creates a journal `SourceEvent` and runs the classifier; `run-pass.ts` never invokes it (correctly — proposer spec §14 puts crisis upstream of extraction, at ingest). The "existing invariant" is spec prose in the proposer spec, not machinery. Intake — the first production ingest path — must build the ingest seam (write event → classify → `SafetyFlag` → route), and this spec assigns that to nobody. Additionally unpinned: (a) does the between-screens beat **wait for the crisis verdict** before rendering? (b) on a CRISIS-level answer, does the reflect pass still fire, and is its result **suppressed** — because rendering "I heard two things — one brightened a star" immediately after active ideation is a concrete, foreseeable failure of the calm the product promises; (c) the classifier's model-arbitration call is serial latency stacked in front of the proposer call, and no budget accounts for it.

**Why it matters.** LAW 7 is non-negotiable "even in a demo" (master concept §7 IN #7), and test 3 tests pause behavior atop wiring no spec owns. A builder following §9's build order would reach "per-answer reflect orchestration" with no crisis step in the list at all — §9 never mentions the classifier.

**Recommended action.** The spec should own the ingest contract explicitly: per answer — persist `SourceEvent` → `classifyCrisis` (block the beat on the verdict; state the timeout/degraded posture, noting the classifier's own fail-closed rules) → on CRISIS: suppress/defer the reflect beat, enter the resource surface, remaining sparks wait (the pass may still run or be deferred to resume — pick one and state it; on resume, C-2's merged-summary rule applies) → on non-crisis: fire the pass. Add the crisis step to §9's build order (it must precede "between-screens beat," not follow voice). Test 3 gains: "the beat never renders before the crisis verdict; a CRISIS answer renders no delta celebration."

### M-2. The immediacy pedagogy is carried by model tail-latency, and the spec has no latency budget and no failure posture for the beat

**Observation.** (Per the scope ruling, this challenges the *argument*, not the exception.) The cost half of the argument holds — 7 structurally capped passes per user, ever, is noise. The **calm** half is the exposed flank: the beat is specified as "a one-line result + a 2–3s sky glimpse," but the thing that produces the delta is a full LLM round-trip (plus crisis arbitration per M-1, serial) with realistic p95 in the 8–20s range and an unbounded tail. The spec never states: the latency budget it believes; what the screen shows between submit and result; what happens when the pass exceeds budget; or what the beat says when the pass **throws** (`run-pass` rethrows after marking `status="error"`). The proposer spec's §10.5 posture — re-enqueue with 5/30/120-minute backoff and a gentle notice — is built for async journaling and is structurally unusable inside a paced seven-screen live flow. There is honest zero-*change* copy, but no zero-*result* copy.

**Why it matters.** "Each answer renders its consequence" degrades into "each answer renders a spinner of model-determined length" precisely when the demo room's network is bad — the master concept's §9 rehearsal risk, but for extraction rather than STT. An unhandled thrown pass mid-intake is a blank between-screens beat in the first ten minutes the spec itself calls the whole first impression.

**Recommended action.** Add to §2: a named latency budget (config, e.g. `intake.reflectTimeoutMs`); the waiting state's design stance (the glimpse can *start* — settle animation on the existing sky — while the pass runs, resolving into the delta or into honest catch-up copy); the failure copy rule ("that one's saved — I'll keep listening as we go," with the material folding into the next answer's pass per C-2c, never a silent skip and never a blocking retry); and the rule that intake never surfaces §10.5's backoff-notice machinery mid-flow. State explicitly that a failed reflect never blocks progression to the next spark (the words are safe in the event store; immediacy is the pedagogy, not the integrity).

### M-3. No carriers: intake session state, spark identity, prompt-version stamping, and the skip record are all unnamed — tests 2 and 8 are untestable as written

**Observation.** Verified against `schema.prisma`: `SourceKind.INTAKE_SPARK` exists (good — the "intake tag" claim holds), but there is **no IntakeSession model, no field carrying which of the seven sparks an event answers, and no `intakePromptsVersion` stamp anywhere**. Consequences: (a) §6's resumability ("current prompt, completed set persists") has no named carrier — test 8 (resume at every prompt boundary) cannot be written; (b) §6's re-run rule ("nothing re-asked that was answered") requires per-event spark identity that doesn't exist; (c) §2's "skipping is data-free (no event written)" collides with test 2's "no telemetry beyond **the skip itself**" and with resume/re-run — knowing spark 3 was *skipped* (so it can be re-offered later) versus *answered* IS persisted data, and its carrier is unnamed; (d) `intakePromptsVersion` is declared versioned config (§1) but stamped on nothing — which prompt wording elicited which answer is unreconstructable, breaking the version-everything invariant (CLAUDE.md) on the one surface where the prompt materially shapes the evidence; (e) voice-vs-text provenance is invisible: `JOURNAL_VOICE` documents its transcript convention, `INTAKE_SPARK` carries nothing saying "this was a reviewed STT transcript," which test 4's byte-equality assertion and any future STT-quality audit both want. The sister specs set the standard here — renderer-lens §7 names every column with its owning migration; this spec, governing two new source trees, names zero schema deltas.

**Recommended action.** Add a "Schema & carriers" section: an `IntakeSession` (or equivalent) row — userId, status, currentPrompt, per-spark status (ANSWERED | SKIPPED | PENDING) with the answering `sourceEventId`, `intakePromptsVersion`, timestamps — with its owning migration; the spark-identity + promptsVersion + input-mode stamp on the event side (a small `meta`/dedicated columns decision, made explicitly; note `SourceEvent.signals` is documented as corroboration-signal space — don't quietly overload it without saying so); and reconcile the skip wording ("skip writes no SourceEvent and no content; it writes only the session-state mark that permits re-offering").

### M-4. The stopping rule is unimplementable as written: no counting predicate, no config keys, and the pass summary can't feed it

**Observation.** §5 counts "7±2 evidence-bearing objects (materialized nodes + forming embers + charged ghosts count; pure hypotheses don't)" with an early close "at ~9," "never before prompt 4." Verified against the code: `ReflectSummary` reports per-pass **deltas** (materialized, forming, ghostsCharged), not standing totals — the rule needs a defined graph query the spec doesn't define. Open questions a builder must not answer ad hoc: is "charged ghost" the renderer spec's link-based predicate (`EXISTS(active link)`) — under which a **CONTRADICTED** mass-0 ghost counts toward "your sky has plenty to begin with" (defensible, since being wrong is the product's claim, but it must be *chosen*); are "forming embers" node-kind `ShadowCandidate` rows at `timesSeen ≥ 1`; do charged-but-still-HYPOTHESIS ghosts (evidence linked, threshold not crossed) count? And none of the three thresholds has a named config key, in a codebase whose CLAUDE.md bans magic numbers and whose test 6 says "the config bound" while no key exists.

**Recommended action.** Define the predicate as a spec'd query (recommended: `COUNT(EXTRACTED nodes, archivedAt IS NULL) + COUNT(node-kind ShadowCandidates) + COUNT(hypothesis nodes WHERE EXISTS(active HypothesisEvidenceLink))` — reusing the renderer's charged predicate by import, not restatement) and name the keys: `intake.targetObjects`, `intake.earlyCloseBound`, `intake.minPromptsBeforeClose`, versioned. Test 6 then asserts against the keys.

### M-5. The beat's and reveal's copy provenance is unpinned — and if composed from raw pipeline output, it bypasses the WOUND veil on the one path where that's live

**Observation.** Two unstated mechanisms: (a) the per-answer one-liner ("I heard two things — one brightened a star your chart placed") and (b) the reveal's "summary of everything heard." If either is model-authored, it is a new untrusted model-touched user surface with no containment spec'd (and the reveal summary would present interpretation as fact — LAW 2's honest-scope note). If deterministic, the spec should say so — and note the one-liner needs node/ghost *identities*, not just `ReflectSummary` counts (available from `matcher.transitions`, but that's a choice to name). The sharper seam: the wedge's own flow (master concept §6.2 — client completes intake *before session one*) means intake can legally run under `PRACTITIONER_SUPPORTED` (verified relationship + consent pre-intake — exactly what `livePolicyFor` checks), where **WOUND is extractable**. Renderer-lens v1.3 makes the veil "a property of the projection… every renderer of the model inherits it," and test 10 pins "the celebration surface cannot bypass the veil." The intake beat and reveal are celebration surfaces this spec creates — and nothing in it says they render from the veiled view model rather than from raw gate/matcher output. A newly extracted WOUND's raw label in a between-screens one-liner at intake is precisely the 1-a.m. failure D-R5 exists to prevent.

**Recommended action.** Pin: beat and reveal copy are **deterministic templates** over pipeline results (no model-authored copy anywhere in intake v1), and any node identity they mention is drawn from the **veiled `SkyViewModel`** (or an equivalently veiled projection), never from `GateResult`/`MatcherRunResult` directly. Add a test-10-shaped assertion: supervised-mode intake answer extracting a WOUND → the beat renders the veil copy, never the label. Also state the drafting provenance for the seed statement (folds into C-1).

### M-6. "STT audio is never stored" is honest about us and silent about the vendor — a claims-discipline gap on the hero path

**Observation.** §3's privacy claim covers our storage only. The named mechanism is the **browser Web Speech API**, which in the dominant implementations ships the raw audio to the browser vendor's cloud for recognition. So the most sensitive words a person may ever speak transit a third party's servers under that vendor's terms — and no document names this: the proposer spec's provider-data-handling duty (§12: documented in the governance bundle "before any real user's journal is sent anywhere") covers the LLM provider and nobody has extended it to the STT provider. The master concept's §8.2 stack note ("Browser STT for the demo; server Whisper later") implies awareness; the intake spec's affirmative "never stored" phrasing reads as a stronger privacy guarantee than the architecture can make.

**Recommended action.** Reword the invariant to what is true and ours ("we never store audio; only the reviewed transcript becomes the SourceEvent") plus one honest sentence naming the browser-STT third-party transit, and add an STT-provider line item to the §7.1 pre-pilot governance bundle (provider, terms, region, retention) parallel to the LLM entry. For September's closed demo this is a consent-copy footnote; for pilots it's LAW 8 work — route it now so it isn't rediscovered later.

## MINOR

### m-1. The extraction mode intake runs under is never stated

`livePolicyFor` makes every fresh signup SOLO; a pre-verified client-of-practitioner (the §6.2 wedge flow) lands PRACTITIONER_SUPPORTED, which flips gate mode (SOLO→SUPERVISED thresholds) and enables WOUND extraction — during intake. Both are probably *correct*; the spec should say one sentence: "intake runs under whatever `livePolicyFor` derives; both modes are in-scope and M-5's veil rule covers the supervised case." Cheap now, confusing in week 6.

### m-2. Zero-change copy needs a two-way split to stay honest

"Held onto that — it'll take shape as themes recur" is honest when `forming > 0` (a ShadowCandidate exists and genuinely will accrue sightings). When the pass verified *nothing* (heard 0, forming 0), nothing was "held" in any graph sense — only the event store has it, and earlier words never retroactively count toward a later theme's recurrence. Split the copy: forming>0 → the current line; all-zero → "saved — nothing new took shape from this one yet." (In scope per the orchestrator notes: this is the honesty of the zero-change copy system, not wording.)

### m-3. Reduced-motion posture for the glimpse and reveal is unstated

Renderer-lens mandates `prefers-reduced-motion` → no animated transitions, with the list view as the canonical accessible surface. The intake's pedagogy is delivered by a 2–3s animation and a "slow settle" reveal. The one-line summary means the *information* isn't motion-only (good), but the spec should state the reduced-motion beat (text result + static sky diff or list-view delta) so the first ten minutes aren't the one place the accessibility contract silently lapses.

### m-4. The eval corpus contains no spark-shaped fixtures

The proposer spec's corpus is journal-shaped. The seven sparks elicit a distinct genre (second-person-prompted, oral, narrative, 30–200 words) and the September demo's fate rides on extraction fidelity over exactly these seven shapes. Add ≥7 hand-labeled spark-answer fixtures (one per prompt, including one skip-adjacent thin answer and one rambling voice-style transcript) to the corpus before the intake build starts — this is the cheapest possible rehearsal of "does the pipeline produce a map a person recognizes" for the input distribution that actually matters on the 23rd.

## ENHANCEMENT

### E-1. Per-prompt yield telemetry, aggregate-only

Track per `intakePromptsVersion` × spark-index: pass yield (heard/forming/rejected), skip rate, early-close rate — the tuning instrument for Jacob's editorial passes, mirroring the proposer spec's rejection telemetry. Aggregate per prompt version only; never per-person (LAW 6: this must never become disclosure-depth scoring, and saying so in the spec is what keeps it structural).

### E-2. Reuse `countUnextractedSources` for honest catch-up copy

The entry point already exposes exactly the number the C-2c/M-2 failure copy needs ("catching up on your last 2 answers…"). Name it in §2 so the honest-copy rule has a carrier instead of a vibe.

## What's genuinely strong

- **The pipeline-reuse keystone genuinely holds at the code level — better than the spec claims.** `run-pass.ts` already includes `INTAKE_SPARK` in its kind allowlist (line 98), and `ReflectSummary` maps one-to-one onto the promised between-screens vocabulary (heard / forming / materialized / ghostsCharged / linksCreated — even "brightened a star your chart placed" has its exact counter). The single-entry-point bet is real, verified, and the right architecture; the deterministic one-liner is buildable from what the entry point already returns.
- **The LAW 6/7 posture is right by construction:** unpenalized skip, no wound-origin questions ever, and a becoming ceremony that is consent-gated with the person's edited words as the only source. Test 5's "decline leaves zero becoming artifacts" is exactly the right negative assertion.
- **Voice-lands-last is the best delivery-realism decision in the spec.** Building text-first means cut-line item #1 (master concept §7) is pre-built rather than retrofitted under week-8 panic, and test 4's byte-equality transcript-ownership assertion targets precisely the right layer.
- **The sanctioned batching exception is argued honestly and bounded structurally** — seven prompts are a real cap, not a config promise, and the spec's framing of intake as "the tutorial for the core loop, not a form" is the master concept's §5.1 rule taken seriously rather than decoratively.
- **The stopping rule's shape** (early *graceful* close, never before prompt 4, "the rest will wait for you") is mastery-mechanics design done right — it needs carriers (M-4), but the instinct to stop while the sky feels like a beginning is the product's voice.
