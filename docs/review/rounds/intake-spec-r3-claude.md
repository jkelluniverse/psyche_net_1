## MAJOR

**M-1. Abort-on-timeout has no point of no return — the abort race can reopen forged recurrence, the exact stake the guard exists to kill.**
§2.3 rules: on timeout "the orchestrator aborts the pass server-side and marks the run `error`: the watermark holds and the fold-forward copy is true by construction." But the pass is a multi-stage async pipeline (`run-pass.ts`: proposer call → gate → `writeGateResult` **in its own transaction** → run-status update to `complete` → matcher transaction), and the spec never says at which stages an abort is honorable. If the abort lands in the window **after the writer's transaction has committed but before the run row is marked `complete`** (or clobbers a `complete` in flight), the result is `status = error` with sky mutations already committed: the watermark holds, so the next pass re-extracts the same sources — re-sighting shadow candidates inflates `timesSeen` (a node can materialize from one utterance), and a model proposing *different* spans of the same utterance mints new Evidence rows that add mass (the writer's evidence dedupe is span-exact and cannot catch this). "True by construction" is claimed, but the construction is not given — and without it, v1.2's fix for the timeout lie creates a narrow path to the forged recurrence that test 9 calls the keystone stake.
**Why it matters:** the whole §2.1 edifice ("one utterance counts once") is only as strong as the abort's atomicity; this is the demo's most likely degraded path (slow model at demo time) crossed with its most protected invariant.
**Action:** two sentences in §2.3 + a test-10 extension: (i) the abort is a **checkpoint honored only before the write stage** — a pass that has entered the writer's transaction runs to completion, is marked `complete`, and narrates as an honestly-labeled catch-up (the existing reject-into-waiting posture already covers the UX; late ≠ aborted); (ii) the run's `complete` transition commits **inside the writer's transaction** (atomic with the mutations — also closes the pre-existing crash window between writer-commit and status-update in `run-pass.ts`, which under the watermark rule is the same double-extraction bug with no timeout needed). Test 10 gains the race case: abort raced against the write stage yields either `complete` + narrated or `error` + zero graph mutations — never `error` + mutations.

**M-2. The §2.1 guard turns a crash-orphaned `running` row into a permanent, silent, per-user extraction lockout — and nothing owns recovery.**
The partial unique index on `ExtractionRun(userId) WHERE status='running'` makes a second pass "fail fast deterministically." §2.3's companion posture assumes the abort always lands ("it proceeds when the abort lands"). But the process that would mark the run `error` can die without marking it — deploy, OOM, platform-level function timeout — and then the `running` row is immortal: every future submit, intake or journal, fails the guard forever. Before v1.2 an orphaned `running` row was harmless (only `complete` advances the watermark); the round-2 integration silently converted it into a wedge. No lease, staleness rule, or reaper is named anywhere; no test covers it. Mid-intake, the person is stuck at "waiting" for the rest of their sparks with copy promising "I'll keep listening as we go" — permanently false.
**Action:** name the staleness rule in §2.1 (e.g., a `running` run whose `startedAt` is older than `intake.reflectTimeoutMs` + a named grace is dead by definition; the next caller marks it `error` before creating its own run — deterministic, versioned config, no daemon needed) and extend test 9 with the orphaned-row case (crashed run → next submit recovers and proceeds; sources not stranded, not double-extracted). Note this rule must compose with M-1's checkpoint: a stale run past the write checkpoint is reaped to `complete`-shaped truth, not `error`.

**M-3. The ceremony write has a crash window §4 leaves unowned — and unlike every other SELF entry, a stranded declaration has NO fold-forward path, by v1.2's own design.**
§4 as written is two steps: "the declaration write routes through the same ingest step as everything else: classify → persist with the verdict" (the SourceEvent lands), then "the lane writes through `writeBecomingDeclaration`" (node + evidence + meta). Nothing states these are atomic. A crash between them leaves a persisted `BECOMING_DECLARATION` event with no node, no evidence, no error surfaced, no retry owner — and v1.2's own A-6 fix (extraction-ineligibility, test 14) guarantees this orphan can *never* ride a later pass. §2.3's "aborted ≠ lost — the material genuinely folds into the next pass" is the safety net for every other failure in this spec; the declaration is the one SELF text deliberately cut out of that net, so its partial-failure posture cannot be inherited — it must be stated. Rounds 1 and 2 each found one unowned becoming seam; this is the remaining one.
**Action:** one sentence in §4: `writeBecomingDeclaration`'s transaction spans the SourceEvent create + node + evidence + intake-meta row (crisis classification runs before the transaction, per §2.2's order — the verdict rides the create). Extend test 5 with the crash-shaped assertion (mid-ceremony failure ⇒ zero becoming artifacts *including the event*, retryable; success ⇒ all four rows, one transaction).

**M-4. §2.2 places the crisis verdict's latency "inside §2.3's budget," but §2.3's abort posture is structurally unable to cover the classify stage — and the classifier can hang.**
The timeline is classify → persist → pass → beat. §2.3's abort semantics are defined entirely over the *pass*: "aborts the pass server-side… **aborted ≠ lost — the event persists**." If `intake.reflectTimeoutMs` elapses during the pre-persist classify stage, there is no run to abort and no persisted event — "the event persists" is false at exactly the moment the spec's calm-under-failure promise matters most. And this is not hypothetical: verified in `src/engine/crisis/classifier.ts` + `config.ts`, the model arbitration call has **no timeout** — the fail-closed posture covers a *thrown or absent* model, not a hung one, so a stalled provider call blocks persist indefinitely. §2.2's "classifier failure posture is the classifier's own; intake adds nothing and removes nothing" quietly assumes the classifier converts hangs into failures; nothing does.
**Action:** (i) a named config timeout on the classifier's model call (crisis config, not intake's) — expiry = model failure, which drops into the classifier's *existing* fail-closed rules (soft-signal → CRISIS; no signal → NONE + degraded), so classification always terminates and persist always proceeds; (ii) one sentence in §2.3 scoping `intake.reflectTimeoutMs` to start at pass start (post-persist), so "the event persists" is true by construction of the budget's own scope. The journal inherits (i) for free.

**M-5. Tripwire (charter hard rule): v1.2's `SourceEventIntakeMeta` stamping duties landed with no test carrier — none of the 15 tests asserts a single meta stamp.**
§6.1 names the carrier and its stamps (sparkIndex, `intakePromptsVersion`, `inputMode`, `becomingSeedTemplateVersion?`); §4 rules the template version "is stamped on the declaration's intake-meta row"; §6.1's rationale is the version-everything invariant ("which prompt wording elicited which answer is reconstructable forever"). Test 1 asserts only `kind = INTAKE_SPARK`; tests 4/5/8 touch content, artifacts, and resume — no test anywhere asserts a meta row exists or carries correct stamps. The charter's auto-adopted rule is explicit ("every grammar/behavior rule lands with its §-tests carrier in the same edit"), and this is the exact class it fired on at renderer-lens v1.3. An unstamped meta row fails silently forever — editorial prompt changes become historically unreconstructable with every test green.
**Action:** add test 16: every answered spark's SourceEvent has a meta row with correct sparkIndex/promptsVersion/inputMode; the declaration's meta row carries `becomingSeedTemplateVersion`; a skipped spark has none (pairs with test 2). While in the test list: extend test 6 to cover `intake.targetObjects`' consumer (the reveal-copy calibration) — v1.2 added the consumer to close "a named key nothing reads," and it is currently the one §5 key test 6 doesn't touch.
